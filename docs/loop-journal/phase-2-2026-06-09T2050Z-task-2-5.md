## What changed

New files:

- `apps/studio/src/lib/sf/ipcTypes.ts` — channel payload types
  (`SfConnectResponse` etc.) split out from `SfConnectionManager` so preload
  and renderer import shapes without pulling jsforce / TypeORM / `electron`
  main-process code into their bundles. `SObjectSummary` / `SfConnectInfo`
  moved here; `SfConnectionManager` re-exports them (`export type`) so the
  Task 2.4 surface is unchanged.
- `apps/studio/src/lib/sf/ipcHandlers.ts` — `initializeSfHandlers()`
  registering `sf:connect`, `sf:disconnect`, `sf:listSObjects`, `sf:status`,
  mirroring the `initializeFileHelpers()` pattern. Errors are sanitized
  before crossing the bridge: `cause` is stripped (not reliably
  structured-cloneable); `kind` / `message` / `port` survive.
- `apps/studio/src/lib/sf/env.ts` — `.env.local` loader (repo root or
  `apps/studio` cwd; existing `process.env` keys win; silent no-op when the
  file is absent). Hand-rolled ~30 lines: dotenv is only a *transitive*
  dependency here and the PRD's file format is trivial. Closes the gap
  flagged in the Task 2.4 journal — previously nothing loaded
  `SF_CLIENT_ID` / `SF_CLIENT_SECRET` into the main process.
- `apps/studio/src/store/modules/SfModule.ts` — namespaced Vuex module
  (`sf/`): state for the single active connection (Q2 default), sObject
  list, loading flags, and `lastError: SfAuthError` for the Task 2.3 dialog
  to branch on. Actions `connect` / `disconnect` / `loadSObjects` /
  `refreshStatus` call `window.main.sf.*`.
- `apps/studio/tests/unit/lib/sf/env.spec.ts` — 6 tests for the env parser
  and loader (comments, quoted values, inline comments, malformed lines,
  env-wins precedence, missing-file no-op).

## Anything surprising

1. **`window.main` is effectively untyped in the renderer.**
   `src/@types/bridge.d.ts` declares `main: typeof api` but the `api` import
   is commented out ("breaks license"), so the symbol is unresolved and
   `window.main.sf.*` calls in `SfModule` typecheck as `any`. Pre-existing
   condition, baseline-invisible. Worth fixing when the licensing concern is
   understood; until then the `ipcTypes` annotations on the preload methods
   are the real contract.
2. **`initializeSecurity()` / `initializeFileHelpers()` only run in the
   no-positional-args startup path** (`app.on('ready')` else-branch).
   Launching `soql-manager file.db` would skip them. Not touched (out of
   scope), but flagged — the sf handlers intentionally register at module
   scope to avoid inheriting the pattern.
