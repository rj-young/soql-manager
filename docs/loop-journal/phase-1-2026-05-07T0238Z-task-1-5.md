## Headline

## What changed

### Modified

- `apps/studio/src/lib/db/types.ts` —
  - `DatabaseTypes` constant: 23 → 1 value (`['salesforce']`).
  - `ConnectionType` type alias narrowed automatically.
  - `ConnectionTypes` UI-list constant: 23 entries → 1.
- `apps/studio/src/common/appdb/models/saved_connection.ts` —
  - `parseConnectionType()` simplified — dropped the `psql` / `postgres` / `mssql` aliases since none are valid `ConnectionType` values anymore.
  - `defaultPort` getter: 22-case dialect switch → returns `null`. SF OAuth loopback runs on a fixed port (1717) handled by `oauth.ts`, not by this model.
  - `defaultSocketPath` getter: dialect-specific Unix socket paths (mysqld.sock, postgresql, tidb.sock) → returns `null`. Salesforce has no socket concept.
  - `parse(url)` method: 90-line connection-string parser (Postgres protocol, SQL Server TrustServerCertificate, SQLite file-extension matching, CockroachDB JWT options, Redshift hostname detection, etc.) → 6-line stub that returns `false`. Phase 2 Task 2.3 builds proper My Domain URL handling in the connection dialog.
  - `checkSqlite()` `@BeforeInsert/@BeforeUpdate` hook removed (was a SQLite-specific validation).

### Added

- `apps/studio/src/migration/20260507_drop_legacy_dialect_connections.js` — deletes rows from `saved_connection` and `used_connection` where `connectionType != 'salesforce'`. Idempotent. No-op on fresh installs (table empty). Existing dev installs see their legacy connections cleared on next launch.
- `apps/studio/src/migration/index.js` — registered the new migration in the `realMigrations` array.

## Anything surprising

1. **The build was unaffected by the type narrowing.** TypeScript types aren't enforced (esbuild strips them). Code that does string-comparison on `connectionType` (e.g. `if (this.connectionType === 'sqlite')`) becomes structurally unreachable but compiles fine. tsc would surface dozens of "this comparison is always false" warnings — but tsc is already red on baseline (Task 0.1 finding), and we re-enable it as a hard gate at end-of-Phase-1 per PRD §7 amendment.

2. **`saved_connection.ts` has many vestigial columns** (`host`, `port`, `defaultDatabase`, `socketPath`, `sshHost`, `sshKeyfile`, `sshBastionHost`, `azureAuthOptions`, `iamAuthOptions`, `redshiftOptions`, etc.). I left them in place. They become dead columns in the SQLite app DB; storage cost is trivial, refactoring them is broader scope than 1.5. Phase 2 Task 2.2 adds the new SF columns alongside (`myDomainUrl`, `instanceUrl`, `userId`, `orgId`, `tokenCacheId`). A future cleanup task can drop the dead columns once we're past Phase 2.

3. **One match remains in `Connection.ts:59`** — `type: 'better-sqlite3'`. Considered making the spec's done-when grep more specific, but documenting the false positive in the journal is cheaper than amending the PRD again.

4. **Migration approach: delete legacy rows rather than rename / coerce.** PRD §1.5 said "drop the legacy connection rows OR rename the column." Dropping is the cleaner choice for a community fork with no production users — there's no path to make a legacy `postgresql` row into a working `salesforce` row, and leaving them around clutters the connection list. Existing dev installs see their old connection list cleared; new installs are unaffected. Saved tokens (in `token_cache`) survive the migration in case they were keyed via something we want to recover; Task 2.2 wires `token_cache` to the new SF connection model.
