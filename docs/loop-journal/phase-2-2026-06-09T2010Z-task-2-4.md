## What changed

Three new files:

- `apps/studio/src/lib/sf/oauth.ts` — OAuth 2.0 Web Server flow. Loopback
  listener bound to `127.0.0.1` (default port 1717, `SF_OAUTH_REDIRECT_PORT`
  override), `state` CSRF check, browser launch via lazily-required
  `shell.openExternal`, code-for-token exchange against
  `<myDomainUrl>/services/oauth2/token`. Returns `SfResult<SfTokenResponse>`
  per the Task 2.4a contract: `EADDRINUSE` → `port_in_use`,
  `?error=access_denied` → `user_denied`, non-https URL → `invalid_url`,
  everything else (incl. network failures, per POC scope) → `unknown` with
  the full Salesforce response body captured in the message. `openExternal`
  and `fetchFn` are injectable so the module loads and tests under plain Node.
- `apps/studio/src/lib/sf/SfConnectionManager.ts` — main-process registry of
  live `jsforce.Connection`s keyed by `saved_connection.id`. First connect
  runs the OAuth flow, parses orgId/userId from the identity URL, persists
  tokens via `tokenStore.writeTokens`, and updates the post-auth metadata
  columns (`instanceUrl`, `orgId`, `userId`, `tokenCacheId`). Reconnect
  rebuilds the connection from stored tokens and validates via
  `conn.identity()` (jsforce auto-refreshes on 401; a `refresh` listener
  persists rotated access tokens). `listSObjects()` filters
  `describeGlobal()` to `queryable === true`, maps to
  `{ name, label, custom, queryable }`, sorts by `name`. `disconnect()`
  clears in-memory state only — no token revocation, per spec.
- `apps/studio/tests/unit/lib/sf/oauth.spec.ts` — 10 tests covering the Task
  2.4 "Done when" (mocked HTTP listener + token endpoint): auth-URL shape,
  secret never in the URL, happy path end-to-end on an ephemeral port,
  `user_denied`, state mismatch, `port_in_use` (real `EADDRINUSE` against a
  blocker server), non-2xx exchange body capture, missing `refresh_token`,
  `invalid_url`, and callback timeout.

## Anything surprising

1. **Task ordering deviation, deliberate:** PRD order is 2.3 (dialog UI)
   before 2.4, but the established cloud/local split (commit `26a4dcc7`)
   defers UI work to local. Task 2.4's main-process code is the only
   remaining Phase 2 chunk that's both writable *and* test-verifiable in the
   sandbox, so it landed first. 2.3 does not depend on 2.4's internals —
   the dialog wires to IPC channels (2.5), not to these modules directly.
2. **The repo compiles without `strictNullChecks`,** under which
   `if (result.ok) return; result.error` does *not* narrow a discriminated
   union (literal comparison `result.ok !== false` does). The spec uses the
   literal-comparison style with a comment. Worth knowing for every future
   consumer of `SfResult` — renderer code branching on `.kind` should use
   `=== false` / `if-else on .kind`, not bare truthiness early-returns.
3. **Nothing loads `.env.local` yet.** `SfConnectionManager` reads
   `SF_CLIENT_ID` / `SF_CLIENT_SECRET` from `process.env` and returns a
   typed, actionable `unknown` error when missing — but the main process has
   no dotenv wiring. Task 2.5 (IPC plumbing, which touches
   `src-commercial/entrypoints/main.ts` anyway) should add it, otherwise the
   first manual Connect will fail with the missing-credentials error.
4. **jsforce 3.10.14** resolved from the `^3.0.0` range. Named exports
   (`Connection`) and the v3 API (`identity()`, `describeGlobal()`,
   `on('refresh')`) verified against the installed package. PRD suggests
   pinning exact; left as-is pending the local handoff where the lockfile
   gets its final native-module resolution.
